# 詳細設計

> Design notes for upcoming changes, written in Japanese.

Issue を実装する前に、その詳細設計をここに書く。1.0.0 までの設計書は、非公開の開発用リポジトリに残している（作者の Vault の状況が書かれているため、このリポジトリには入れていない）。

## 1. 書かないもの

このリポジトリは公開している。設計書にも、コミットメッセージや PR の本文にも、次のものを書かない。

- 本名、個人のメールアドレス。コミットの作者は GitHub の noreply のアドレスにする
- ホームディレクトリなど、手元の環境の絶対パス。パスは `<Vault>/…` か、Vault の中の相対パスで書く
- 作者の Vault の中身：ノートの名前と本文、デッキ名、フォルダの構成、ノートの件数、試験日
  - 例が要るときは、[`docs/examples/`](../examples/) のサンプルか、架空の名前（`Deck A`、`Notes/Topic.md` など）を使う
- ほかの人の Vault やノートの中身（Issue に貼られたものを含む）。設計に要る形だけを、架空の名前に置き換えて書く

push の前に、送るコミットを手元で検索し、上のものが0件であることを確かめる。検索語（本名、個人のメールアドレス、ホームディレクトリのパスなど）はこの文書に書かず、手元で埋める。

```sh
git log -p origin/main..HEAD | grep -c -i -E "<検索語1>|<検索語2>"
```

## 2. 置き場所と名前

- `docs/design/<Issue の番号>-<名前>.md`（例：`11-tag-decks.md`）。番号は、このリポジトリの Issue の番号
- 優先度でフォルダを分けない。優先度は Issue のラベル（`P3` など）で表し、あとから変わることがある

## 3. 書式

次の見出しで書く。コードの位置は `ファイル:行` で示す。

```markdown
# #<番号> <タイトル>：詳細設計

- Issue：#<番号> ／ 優先度：P<n> ／ 前提：#…

## 1. 目的と完了条件
（受け入れ条件を、確認できる形で箇条書き）

## 2. 現状
（該当するコードと、何が問題か）

## 3. 方針
（採用する方法と、採らなかった方法とその理由）

## 4. 詳細
### 4.1 変更するファイル
### 4.2 型と関数（TypeScript のシグネチャ）
### 4.3 処理の流れ
### 4.4 UI（文言、表示の条件、CSS、狭い幅とタッチ操作）
### 4.5 設定とデータの互換性

## 5. エッジケースとエラー処理

## 6. テスト
### 6.1 ユニットテスト（ケースの表）
### 6.2 手動での確認手順

## 7. 実装の手順（コミットの単位）

## 8. やらないこと・残るリスク

## 9. 判断してほしい点
（作者に決めてもらう必要があるもの。なければ「なし」）
```

## 4. 変えないもの

公開した後は、使っている人の Vault や設定に残るので、変えにくい。

- frontmatter のキー：`study-deck`、`study-next`、`study-stage`、`study-history`、`study-suspended`。履歴の書式（`YYYY-MM-DD ok|hard|ng|new`）も同じ
- コマンドの ID（`open-study-board`、`start-review`、`enroll-current-note`、`create-review-note`、`unenroll-current-note`、`grade-*`、`toggle-suspend-current-note`）。ホットキーの割り当てが ID に結びついている
- コードブロックの名前（`study-today`、`study-progress`、`study-forecast`）と、ビューの種類（`study-curve-board`）
- 公開 API：`plugin.getDueQueue(deckName?)`
- 設定（`data.json`）の形を変えるときは、`src/settingsMigration.ts` の先頭に書いた手順で移行を足す。項目を足すだけなら移行は要らない

## 5. 書き方の約束

- `minAppVersion` は 1.7.2。これより新しい API は使わない
- 本文の書き換えは `Vault.process`、frontmatter は `FileManager.processFrontMatter`、組み立てたパスは `normalizePath` を通す
- `el.style.*` に値を直接入れない。データで変わる値は `setCssProps` で CSS 変数として渡す
- CSS のクラスは `study-curve-` で始める
- コマンドの ID にプラグインの ID を含めない。既定のホットキーを付けない
- 非公開の API（`app.setting`、`app.plugins` など）は使わない
- UI の文言は今は日本語だけ。新しく足す文言は、各モジュールの先頭の定数（`TEXT` など）にまとめる（#4 の多言語化で移しやすくするため）
- 通知の文言
  - 成功：`{ノート名}：次回 9/29(火)`、`{ノート名} を 9/29(火) に送りました` のように、何がどうなったかを書く
  - 失敗：`{操作}に失敗しました：{エラーの内容}`
- `npm run build` は環境変数も `.env.local` も読まず、副作用を持たない（ディレクトリの審査が、同じビルドを再現できるように）
- 開発中のビルドは、確認用の Vault に `npm run dev` と `OBSIDIAN_DEV_PLUGIN_DIR` で入れる。作者がふだん使う Vault には入れない（公開版を Obsidian の更新で入れる）

## 6. ブランチと PR

| | 設計の PR | 実装の PR（設計のマージの後） |
| --- | --- | --- |
| ブランチ | `design/<番号>-<名前>` | `feat/<番号>-<名前>` または `fix/<番号>-<名前>` |
| 中身 | `docs/design/<番号>-<名前>.md` だけ | コードと、必要ならテストと README |
| タイトル | `設計: #<番号> <Issue のタイトル>` | Issue のタイトル |
| 本文 | 概要、判断してほしい点、`Refs #<番号>` | 変更点、確かめたこと、`Closes #<番号>` |
| ラベル | `設計`、優先度 | 優先度 |

- コミットメッセージは日本語で書く
- 実装の PR は、`npm run lint`、`npm run build`、`npm test` が通り、確認用の Vault で動きを確かめてからマージする

## 7. レビューの観点

- 変えないもの（§4）に触れていないか
- 完了条件が、実機で確かめられる形になっているか
- エッジケースに、ほかの人の Vault（大量のノート、タスク管理のチェックボックス、CRLF の改行、日本語以外のファイル名、深いフォルダ）が入っているか
- テストのケースが、完了条件と対応しているか
- 書かないもの（§1）が入っていないか
